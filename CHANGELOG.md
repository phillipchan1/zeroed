### One-time re-check of v1.1 persistent blocks under v1.2 (Round 3 PR B, section 11b), tracks_v1

An operator-run system job, not a Worker route: nothing in `/api/session-rx`, the MCP tool list, the app or any route changes, with the flag on or off. Only athletes with `tracks_v1` on are read or written. No schema change.

- **What it re-checks.** Per athlete, each region whose latest `region_status` row is an open block written by a check-in under methodology v1 / v1.1 (or with no version on record). v1.2-stamped blocks and re-blocks the athlete made by undoing a clinician clear are not touched.
- **The decision (pure, `decide()` in `worker/src/reevalV11Blocks.ts`).** Under 18 or no age on file: kept (v1.1 behaviour). Otherwise the report that set it and every report of that region since are judged by v1.2's own U7 call (`evaluateReport`): a red flag, > 5 twice within 14 days or a rating rising across 3 sessions keeps it persistent. Anything else is lifted: a new `region_status` row (`ok`) supersedes the block, plus one `change_log` row per lift (actor `system`, `job:reeval_v11_blocks`, methodology `v1.2`, before → after, U7). If the v1.2 temporary window (that day and the next logged session, ≤ 14 days) is still open, readiness derives the temporary block from the report as for any v1.2 block; otherwise the region is unblocked. Nothing is deleted or edited.
- **Undo.** The lift is a normal Changes-feed row: the athlete's undo makes the block persistent again (`apply_block_reeval` revert handler); redoing it is refused, like redoing a clinician clear. A coach without health access sees neither row's content (target `region`).
- **Idempotent.** Each athlete re-checked gets one `apply_block_reeval_run` marker row (counts only) and is skipped from then on. Each write in the batch re-checks in SQL that the block is still the open latest row, the flag is on, the age inputs and pain reports haven't moved since the plan, and no marker exists; an advisory lock serializes concurrent runs.
- **Runner.** `scripts/reeval-v11-blocks.mjs`: reads `DATABASE_URL` (never printed), talks to Neon's HTTP SQL endpoint (`POST https://<host>/sql`, batch = one ReadCommitted transaction), dry run by default, `--apply` writes everything in one batch. Output is counts by region and totals only.
- **Weekly review.** `blockedDuring` ends a block where a later status row superseded it (only this job writes one over an open block).
- **Checks.** `worker/src/reevalV11Blocks.check.ts` (every criterion kept vs lifted, minors / unknown age never lifted, idempotency, mid-batch failure writes nothing, drift between plan and apply, revert re-persists, output has no health detail, A/B isolation, flag-off athletes untouched, the HTTP request shapes); `reverts.check.ts` covers both new types. Synthetic data only.

**Deploy:** after the Worker with this change is live, run `worker/schema/ops/confirm-adult.sql` first (a known adult with no age on file is otherwise "unknown" and keeps every block), then `node scripts/reeval-v11-blocks.mjs` (dry run), read the counts, then `--apply` once. **Rollback:** per block, the athlete's undo of its change_log row re-persists it. Per athlete, turning `tracks_v1` off turns readiness off entirely (no block of any kind applies, as before). Redeploying the previous Worker is safe (it reads the superseding `ok` row as the region's status, as this one does) but has no undo handler for the new rows, so per-block undo needs this Worker. Nothing to drop: no schema change.

### Composed blocks write the week's exercises (Round 2 item 6, G6 follow-up), coach_v1

Behind `athlete.flags.coach_v1` (which only counts with `tracks_v1`), still off for everyone. With it off the MCP tool list, every tool, `/api/session-rx`, the app and every route are exactly as before.

- **The block's week becomes sessions.** `worker/src/coach/blockProgram.ts` (pure, deterministic) turns the composer's week layout into one routine per training day: lifts (the priority goal's lift on the priority track, the rest on Other lifts at maintenance; ~1/3 volume at maintenance, U2), power (jumps sized to the block's contact budget, then acceleration starts, U8/U14), aerobic (bike unless the block runs), repeat sprints as a bike interval block (HIIT, U9), and the block's prehab items (already capped per session). Sets, reps and RPE targets come from the engine; no load is written, so `/api/session-rx` computes it from the block's tracks and rules (#49).
- **One preview, one approval.** `preview_composed_block` shows the concrete program diff and runs the G5 validators on it as an explicit `rewrite=true` (U13 doesn't apply to a composed block, and the preview says so); a red flag (U7) still refuses it. The athlete's single approval covers the whole block; `apply_composed_block` writes everything in one transaction with one change_log row (methodology + module versions, `diff.program_phase` with the generator version). A preview whose live program moved since is refused.
- **Never overwrites the live program.** The sessions go into a new queued block (a `pending` phase from the block's start, promoted by the app as any queued block is); the live block keeps running and ends the day before. A re-compose before the start skips (keeps) the previous block's queued phase; anything else queued refuses the apply. `athlete.training_max_overrides` is never touched.
- **Red flags, minors, prehab.** No written exercise loads a blocked region (it is listed as held; a coach without the health toggle sees a count, not the region). Under 18: no target RPE above the minors' cap, contacts within the minors' ceiling (tightened caps tighten the sessions). Prehab only from the capped list.
- **Revert.** Undoing the block (Changes feed) skips its queued phase (kept, routines stay as history), puts the live block's end date back and re-queues the phase it replaced; once the block has started, the previous block is live again.
- **App.** The block preview the athlete approves lists the sessions and any held work.
- **Schema (additive).** `composed_block.phase_id` (nullable, no FK). Before it exists blocks apply exactly as before (no sessions) and the preview says why.
- **Checks.** `worker/src/composedBlockProgram.check.ts`. Synthetic data only.

**Deploy:** hand-apply `worker/schema/composed-block-program.sql` on Neon (`supabase/migrations/20261104000012_composed_block_program.sql` on Supabase) after `coach-v1.sql` and `change-tombstone.sql`. Rollback is in the SQL header.

### Offline session-RPE queue + rating last night's session after midnight (Round 2 item 4, G9 follow-up), tracks_v1

Behind `athlete.flags.tracks_v1`; with it off the app queues nothing, `/api/session-rpe` answers 404, and `/api/session-rx`, the MCP tool list and every tool are exactly as before.

- **Queue.** The finish's CR-10 tap is written to the device first (`src/lib/sessionRpeQueue.ts`, localStorage like the workout outbox) and then sent; one that can't be sent waits and is retried on launch, reconnect and resume. Accepted (incl. "Already logged") and definitive refusals (refused, 400, 404) leave the queue; no answer, 5xx, 401 and "not set up yet" keep it. A newer tap for the same session and date replaces one still waiting. Today shows "Session effort saved on this device, will sync" while one waits.
- **Idempotent.** Each tap carries a `client_id` and `tapped_at`. A retry of a tap already applied is "Already logged" (no second write or change_log row); a queued tap older than the row's latest is acknowledged, not applied. One row per session per day and update semantics are unchanged.
- **After midnight.** A session dated D can be rated until 04:00 athlete-local on D+1. A queued tap is judged at its own `tapped_at`, trusted only between now − 48 h and now + 5 min, so it can't backdate a rating beyond its date's window.
- **Schema (additive).** `session_rpe.client_id`, `session_rpe.tapped_at` (nullable) and a partial unique index. Before they exist the 04:00 grace works on the server's clock and tap times are ignored.

**Deploy:** hand-apply `worker/schema/session-rpe-queue.sql` on Neon (`supabase/migrations/20261104000011_session_rpe_queue.sql` on Supabase) after `session-rpe.sql` and before deploying this Worker for anyone with `tracks_v1` on. Rollback is in the SQL header.

### Every change type revertible (Round 2 item 3, spec section 6), tracks_v1

Behind `athlete.flags.tracks_v1`; with it off the MCP tool list, every tool, `/api/session-rx` and every read are exactly as before, and `/api/change-log` answers 404.

- **One handler per change type.** `worker/src/reverts.ts` has a revert handler for each of the 29 change_log types the Worker writes (28, plus `revert_change` itself), and `reverts.check.ts` scans the code and fails if one is written without one. A revert is still one logged `revert_change` row (`revert_of` → the row, which gains `reverted_by`), with the athlete's tap as its approval, in one transaction.
- **What reverting means, per kind.** Edits are put back when the target still looks exactly like the change left it: program edits (incl. the in-app editor, now recorded with before/after sessions), proposals, assignments, tracks, rules, goals, block details, training max, methodology overrides, activities, coach role / health toggle. Rows a change created are **retired**, never deleted: a track, a goal, an autoreg rule; an added session comes out of the week (kept), a queued next-week block is skipped and this week's end date put back. Logging is **voided** with a tombstone (append-only tables stay append-only): check-ins and their pain scores, session RPE (a second tap goes back to the first), goal measurements (the goal's numbers go back), notes. A cleared block or red flag is **re-blocked**. Reverting a revert **redoes** it through the same guards.
- **Never reverted, by definition:** revoking a coach (access is never given back by an undo; invite again) and the system's voided preview. Redoing a clinician clear is refused, and so is redoing a composed block (re-compose instead, on the current methodology).
- **Safety.** No revert loosens an under-18 rule (all methodology guards run as the athlete), lifts a red flag, or unblocks a region; voiding a check-in keeps the block it set; a minor's birth date is never undone.
- **Conflicts.** A later change, not since undone, to the same target shows in the revert preview and blocks it ("undo that first"). The athlete's feed previews before applying (`{ action: 'preview_revert' }`), and the tap applies exactly that preview (`{ action: 'revert', preview_id }`) or asks to preview again. A coach without the health toggle can't preview reverting a health row.
- **Feed.** Revert shows on every row that has one: Undo, or Redo on an undo row (`revert_action`). The athlete's own previews don't show as coach suggestions.
- **Schema (additive).** `change_tombstone` (one row per voided or retired row; lifted once on redo). Readers skip a live tombstone only with the flag on, so rollback reads every row as before.

**Deploy:** hand-apply `worker/schema/change-tombstone.sql` on Neon (`supabase/migrations/20261104000010_change_tombstone.sql` on Supabase) after `coach-roles.sql` and before deploying this Worker for anyone with `tracks_v1` on. Rollback is in the SQL header.

Escalates to a human on a red flag, disagreeing twice, or an unresolved rule conflict. Chat lives in `coach_message` (kind `chat`); a "yes" to a preview is the athlete's chat approval (`msg:<id>`, newer than the preview, applies once). Uses the existing OpenAI integration (`OPENAI_API_KEY`); no new provider or env var.

### Readiness + pain check-in (G4), weekly review (G8), coach-read logging, tracks_v1

Behind `athlete.flags.tracks_v1`; with it off `/api/session-rx`, the MCP tool list and every tool are byte-for-byte as before, no check-in card shows, no read is logged, and `/api/readiness` + `/api/weekly-review` answer 404.

- **Daily check-in (manual only).** New append-only `checkin` (sleep h, stress 1–5, soreness 1–5) and `pain_report` (region, 0–10, section 8 red flags). The athlete logs them from a small card on Today; each submission is one `log_checkin` change_log row under `standing:logging`.
- **U6 in the engine.** Flags: today's sleep < 6 h, stress ≥ 4, soreness ≥ 4, plus one more for each 3-day streak (sleep < 6 h 3+ nights, stress/soreness ≥ 4 3+ days). One flag trims accessories a set; two or more also pull HIIT and plyos (cut order HIIT, then accessories). The main lift is never touched. Thresholds come from the athlete's methodology (G3).
- **U7 in the engine.** ≤ cap (3) proceeds; 4–5 drops impact and takes 10% off loaded work for that region; > 5, worse than yesterday (above the cap) or any red flag sets the region `blocked` in `region_status`: nothing loads it, a refer-out notice is returned, and it stays blocked until the athlete marks it cleared by a clinician (athlete only, logged with their tap; no coach, app_coach included, can clear it). Red flags win over a raised cap; a raised cap counts only for an adult and only if the region settled the day before. Region mapping is the G5 classify table; an exercise it can't place, on a day with a blocked region, is flagged rather than silently loaded. Previews refuse loading a blocked region.
- **Structured explanation.** With a check-in, pain report or open block for the date, each prescription carries `readiness` and `adjustments` (`skip` / `trim_sets` / `reduce_load` / `check_region`, each with a reason and `rule_refs`), the response carries `readiness`, and the version strings change so the app refetches. With none, the output is the G3 output exactly.
- **Health data (D3).** `mcp_token.share_health`, default on. The athlete switches it per coach under Profile → Coach access (logged). Off: `get_checkins` / `get_region_status` refuse, `get_weekly_review` omits pain and check-ins, and check-in rows in `get_change_log` are redacted for that coach.
- **Weekly review (U15).** `get_weekly_review(week?)` and `GET /api/weekly-review?week=`: compliance (planned vs logged, target 80%), priority-lift e1RM trend, maintenance held (U12), pain trend, check-in averages, and progress / hold / deload with `rule_refs` and one line of why. Read-only.
- **Coach reads are logged.** Every MCP `get_*` / `list_*` / `search_*` call and every app_coach read appends a `coach_read_log` row (actor, tool, scope) before it runs, and refuses if it can't. The athlete's own reads are not logged. The athlete sees the list under Profile → Coach access.

### Methodology as config (G3), preview validators (G5), proposal created_by (G10 follow-up), tracks_v1

Behind `athlete.flags.tracks_v1`; with it off `/api/session-rx`, previews, proposals and the MCP tool list are byte-for-byte as before, and no new column or table is read or written.

- **One global, versioned ruleset.** `worker/src/methodology/v1.ts` holds U1–U15, the under-18 rules and the 24 h preview expiry as data, version `v1`. Where the engine already had the number (TM 90%, +2.5%/+5% pushes, deload 65% TM @ RPE ≤ 6, 24 h, 30% small-edit cap) the default equals it; the lift model now takes these as optional params and is identical without them. U4 records `e1rm_source: rpe_chart` (what the engine does) rather than Epley.
- **Per-athlete overrides.** New append-only `methodology_override` (athlete, optional track, path, JSONB value, who, approval, preview, change_log row; superseded once). Effective params = global → athlete → track → under-18 clamp. Paths are a closed, typed, range-checked schema. Under-18 rules only tighten; for a minor nothing loosens; the universal pain cap stays ≤ 3/10; the raised cap (≤ 5/10 if settled next morning) is a per-region opt-in that needs a date of birth showing 18+ and is refused on a red-flagged region; a red flag can be set by a coach and cleared only by the athlete; red flags block loading.
- **MCP (flag on).** `get_methodology`, `preview_methodology_override`, `apply_methodology_override` (confirm + preview < 24 h with unchanged diff + the athlete's approval, logged in change_log with `rule_refs`). `preview_session_override` takes `rule_refs` and `rewrite`; `preview_program_edits` takes `rewrite`.
- **Every prescription records its methodology.** Flag on, `/api/session-rx` adds `methodology_version` (`v1`, or `v1+<hash>` with overrides or the under-18 rules) to the response and each prescription, runs the lift model on the resolved params, caps RPE at 8 under 18, and skips exercises that load a red-flagged region. With defaults the numbers and version strings are unchanged. `change_log.methodology_version` is filled on every row.
- **Preview validators.** Program-edit, week-only override and proposal previews return `warnings: [{ rule, message, target }]` for U8 session order, U9 interference (HIIT count, HIIT the day before heavy legs) and U10 supersets (two heavy compounds, press + triceps, anything + plyo, grip + deadlift, top sets ≥ RPE 9, main-lift rest). Only new violations are reported; unknown exercises never warn. U13 (> 30% of the week's exercises changed without `rewrite=true`; one exercise is always surgical) and red flags fail the preview.
- **created_by on proposals.** New proposals record `mcp:<token id>` / `app_coach`; approvals of them name that coach. Revoking a coach now also marks its pending proposals stale (`voided_at`) and voids their unconsumed approvals, logged on the `revoke_coach` row. Older rows (NULL) are left alone.

### change_log, get_change_log, Changes feed and one-tap undo (G2, tracks_v1)

- **One accountable record.** New append-only `change_log` (spec section 6: actor, tool, target, before → after diff, rationale, `rule_refs`, `approval_ref`, `preview_id`, `expires_on`, `reverted_by`, `revert_of`). A trigger refuses every UPDATE except setting `reverted_by` once, and every DELETE except the athlete's own account deletion. `program_revision` and `session_override_log` are still written exactly as before; nothing historic is copied.
- **Every covered write logs one row, in the same transaction or statement:** `apply_program_edits`, proposal Accept (app or MCP), every track / rule / goal / target / block write, `set_training_max` over MCP, week-only override apply and clear (a move is one change), the in-app editor's `program_revision`, voided previews, and coach revocation. `rule_refs` come from `U1`–`U15` named in the rationale or passed as `rule_refs`.
- **Approval everywhere, not just overrides.** Logging (`log_goal_measurement`, `add_workout_note`) is `standing:logging`. Every other confirmed MCP write needs `approval_ref = msg:<id>` and the `preview_id` its preview returned (kept in `change_preview`, under 24 h old, diff — including the target's current state — unchanged); a proposal stands in for the preview and must be under 24 h old. `app_coach` can never approve. Flag-on write tools advertise `approval_ref`, `preview_id` and `rule_refs`.
- **Revocation.** Revoking a coach in the app voids its open previews (both kinds) at once and logs it, in the revoke's transaction.
- **MCP.** `get_change_log(since, target?, actor?, limit?, before?)`: athlete-scoped, newest first, paginated. `preview_revert_change(change_id)`: what an undo would restore, or why it can't; it writes nothing and marks the change as suggested in the athlete's feed. There is no coach-side apply.
- **Undo (athlete only).** `POST /api/change-log { action: 'revert', id }` or `POST /api/change-log/:id/revert`. Restores the target only if it still looks exactly as the change left it (otherwise "changed since"), writes a new row with `revert_of`, sets `reverted_by` on the original, and refuses a second undo. Supported: program edits and proposals applied this week (not ones that queued next week's block or added a session), track updates, progression rules (ended, not deleted), goal definition updates, the athlete target, block details, week-only overrides (voided, kept), and training maxes (only that lift, back to its prior value). Creating a track, goal or autoreg rule, logging, and clears are refused with the reason; nothing is ever deleted.
- **App.** Program → Changes: who (You / Claude or the coach's name / Coach / System), what, why with rule refs, when, an Undo with a confirm, and Undone state. Pull to refresh reloads it.

**Deploy:** hand-apply `worker/schema/change-log.sql` on Neon (`supabase/migrations/20261104000003_change_log.sql` on Supabase) BEFORE turning `tracks_v1` on for anyone, then deploy the Worker. Rollback is in the SQL header: drop the flag per athlete (instant; writes go back to today's path); the tables can be dropped afterwards.

### Week-only session overrides (G1, tracks_v1)

Behind `athlete.flags.tracks_v1`; with it off, `/api/session-rx`, the MCP tool list and the app are unchanged.

- **One date, not the template.** A `session_override` row changes ONE dated session: add, swap, drop or adjust an exercise, or move an exercise or the whole session to another day (a move is a `move_out` row on the source date and a `move_in` row on the target, sharing `pair_id`). Program, phase and routine rows are never written.
- **Engine applies it on that date only.** `POST /api/session-rx` with `date: YYYY-MM-DD` reads that date's active overrides into the session's exercise list before the engine prescribes it, and returns `prescription.override` (the day's list, a mark per changed index, drops and moves, labeled "This week only"). No `date`, no flag, or no override → the old response, byte for byte. An override never applies after `expires_on` (default: the Sunday ending the date's ISO week; at most date + 7). Expired and cleared rows stay for audit.
- **Propose-only writes.** New MCP tools (listed only with the flag): `preview_session_override`, `apply_session_override`, `list_session_overrides`, `preview_clear_session_override`. Preview stores a preview and writes no override. Apply needs `confirm=true`, a preview under 24 h old whose diff (including the resulting session that day) still matches, and `approval_ref`: an MCP coach passes `msg:<id>`, the athlete's own tap is `tap:<id>` minted by the Worker, and standing approval never covers it. `app_coach` can never supply `approval_ref`; it parks a `coach_proposal` (`kind = 'session_override'`) and the athlete's Accept applies it. A coach can't apply a preview parked for the athlete. Previews made by a revoked or expired coach token are void, and the void is logged.
- **Audit.** Every apply and clear writes `session_override_log`, shaped like the spec's `change_log` (actor, tool, target, diff, rationale, approval_ref, preview_id, expires_on) so G2 can lift it across.
- **App.** Train shows a "This week only" badge on an overridden session and, in its sheet, the day's list with a badge on each changed exercise; Program's session list shows the same badge. Proposal cards for overrides say "This week only."

**Deploy:** the Worker (`npm run cf:deploy`) and `worker/schema/session-override.sql` hand-applied on Neon (`supabase/migrations/20261104000002_session_override.sql` on Supabase). Until the tables exist, session-rx ignores overrides and the tools report them unavailable. Rollback is in the SQL header: drop the flag per athlete; the tables can be dropped afterwards.

### Goals at the center (tracks_v1)

Everything here is behind `athlete.flags.tracks_v1`; flag-off athletes see no change.

- **Status in the brand's colors.** Goals read Zeroed (confirmed), On course (text), Off course (signal), or Needs a test (pending), each with its own mark shape. Status comes from a forecast: least squares over the last three real measurement days (spanning at least a week), projected to the due date, so a stalled lift is off course weeks out instead of only inside 21 days. A goal tested on a cadence needs a test once the cadence lapses. MCP `get_goals` / `get_goal_history` return the same `display` and `forecast`.
- **Lanes by glyph.** Tracks draw their stored `icon` instead of a color that matched a status token.
- **Sets move goals.** `athlete_goal.source_metric` is a typed binding (`e1rm:`, `top_set:`, `reps:`, `distance:`, `time:`, `rounds:`, `test:`), inferred only when a goal's name matches an exercise exactly; `upsert_goal` validates the kind and that the goal's unit can be reached. Committing a session writes a `workout_log` measurement for each goal it held or beat (client_key `wl:{workout}:{goal}`), even when the outbox syncs before the flag loads; editing the session corrects or removes that measurement and recomputes current and best. Train lists the goals each session moves, the workout carries each exercise's goal and locks on a new best, and the finish screen adds Goals moved.
- **Goals is the home of the plan.** Four tabs (Train, Goals, Coach, You); Program is the block's detail under Goals. Goals opens on the athlete's sentence, the goal reticle, the goal that needs you, targets by lane, and the block as a road. Each goal has a page (`/app/goals/:goalId`) with a forecast chart, its lane, measurements, and coach moves. A new block copies named lanes forward and moves goals onto them.
- **Coach moves.** For athletes with the flag, confirmed MCP track, goal, and rule writes record a coach note pinned (`ref_id`) to what they touched, with the rationale.
- **Claude plans from goals.** New `get_goal_brief`. `preview_program_edits` with `propose=true` parks the preview as a proposal; the app shows it on Coach, on the goal it serves, and on the Goals card. Accept (`POST /api/proposals`) or `apply_program_edits(proposal_id)` claims the proposal, applies exactly the stored edits, refuses as stale if the program changed since, and releases it if nothing was written.

**Deploy:** the frontend ships with the build. Proposals need the Worker deployed (`npm run cf:deploy` or the deploy-cloudflare workflow) and `worker/schema/coach-proposal.sql` hand-applied on Neon (`supabase/migrations/20261104000001_coach_proposal.sql` on Supabase). Until both, the tools report proposals as unavailable and the app shows none; everything else works against the current Worker.

### Worker: written load and manual rules beat TM

- `get_lift_model` "This week" uses the session's written `load` (295 / 350). A `manual` progression rule never computes from TM. TM / chart math is the fallback only when no load is written and the rule is not manual. Deploy the Worker to pick this up on refresh — no iOS build required for the Coach / MCP path.

### Session preview: written load and planned order

- Track-grouped preview, active session, and logging defaults show a written `load` (295 / 350) instead of TM / lift-model math (335 / 400). Flag-off uses the same resolver.
- Track groups follow the first exercise of each track in session order. Interleaved tracks fall back to one list so Deadlift stays before Squat.

### tracks_v1 follow-up

- Goal status is recomputed on read. Higher is hit only at `current >= target` (and `<= target_range_hi` when that ceiling is set). Lower is hit only at `current <= target`. Pass is hit only on a pass. Postgres string numerics are coerced so Broad jump 95 / 100 cannot lexicographically compare as hit.
- `last_measured` is the latest real `goal_measurement.measured_on`, or null. Seed `client_key` `seed:*` rows and invented dates (2026-10-01) do not count. No data migration; stored `athlete_goal.status` is ignored on read.

- Named tracks / goals / rules seed is a local gitignored SQL file applied by `scripts/seed-athlete-tracks.mjs` (email from env). Migrations stay schema-only. The `tracks_v1` flag is enabled per athlete with `scripts/enable-tracks-flag.mjs`. Prod data is left in place.
- Personal emails, health notes, and the Phil seed files are out of the public tree.
- Every non-`external` program-create path inserts a General track (app, ComputeScreen, Worker `/api/data`, `create_track`).
- Unstamped `target_rpe = 1` is a Coach / preview proposal the athlete approves. Coach writes stamp `rpe_source`. Never rewritten silently.
- `worker/schema/tracks-v1.sql` matches Neon (`app.sql` style): no RLS / GRANT / `authenticated` / `get_current_athlete_id()`. Double-escaped `\\bohp\\b` and `tm_override_value` decimal regexes use a single backslash.

### tracks_v1 — multi-track programs, structured goals, MCP

Named tracks inside one program, progression / autoregulation rules, structured goals with measurement history, and workout notes. Behind `athlete.flags.tracks_v1`. Deadlift TM is not rewritten. General tracks are backfilled and created in app/seed code — not by an INSERT trigger, so data-only restore stays valid.

New MCP tools: `list_tracks`, `get_track`, `create_track`, `update_track`, `assign_exercise_to_track`, `get_track_progression`, `set_track_progression_rule`, `list_autoreg_rules`, `upsert_autoreg_rule`, `get_goals`, `upsert_goal`, `log_goal_measurement`, `get_goal_history`, `add_workout_note`, `update_athlete_target`, `update_program_meta`.

`preview_program_edits` accepts `week_start` and exercise `track` / `superset_group` / `rest_s` / `contacts`. `add_note` on program edits is still a coach-inbox message; real session notes use `add_workout_note`.
